# 基于多模态交互的学习陪伴助手设计与实现

项目计划书　｜　2026年11月10日

本项目拟开发一款运行于 Windows 桌面的学习陪伴助手。用户主动开始学习后，系统在获得摄像头、麦克风授权的前提下，识别手机使用相关视觉线索、皱眉动作和叹气声音，结合学习时长与用户反馈，由桌宠通过动作、文字气泡及可选语音提供温和提醒。

这里的“多模态”指综合使用视觉、声音和用户输入；“推理”指用已有模型处理新的图像或声音；“融合”指把不同来源的线索放到同一时间窗口内综合判断。桌宠是交互界面，感知与决策模块才是课题的主要技术工作。

推荐采用“本地感知模型 + 可解释的时序规则 + 二维桌宠”的实现路线。先完成能够稳定演示的闭环，再增加对话和个性化能力。计划按单人开发、具备或同步补充 Python 基础、12周有效开发时间安排；若完全零基础，宜额外预留2—4周学习与环境调试时间。

## 一 课题定位与研究目标

### 1.1 要解决的问题

学习者在电脑前自主学习时，可能出现频繁拿起手机、长时间连续学习、皱眉或叹气等现象。常规计时器主要根据固定时间提醒，较难依据当前可观察线索调整反馈。本课题尝试让一个可交互的桌宠结合视觉、声音和学习任务上下文，选择是否提醒、何时提醒及如何表达，并评估这种方式是否准确、易用和少打扰。

图片提供的是产品表现形式：桌面悬浮宠物、动画、对话气泡及点击互动。本项目可以用带透明通道的二维动画做出类似的桌面效果，无须先制作三维模型。截图中的音乐播放器不列入第一版范围；宠物形象、动画及声音应使用原创或具有相应授权的素材。

### 1.2 总体目标

交付一个能够安装运行的原型：用户设定学习任务并开启陪伴，桌宠开始计时；视觉和音频模块输出事件；决策模块结合上下文选择反馈；用户可以回应、纠正误判或暂停感知；系统记录必要的学习和交互摘要。

具体目标包括：完成桌宠交互界面；实现三类目标线索的检测与质量判断；实现带持续时间和冷却机制的多模态决策；通过独立测试数据与小规模用户试用评估识别、实时性和打扰程度。

### 1.3 研究问题与成果边界

研究问题一：与只依赖单一线索的策略相比，联合视觉、音频和任务上下文的策略，能否提高提醒的适宜性并减少误提醒？

研究问题二：个人基线校准、时间窗口和提醒冷却机制，能否改善不同用户、光照及噪声条件下的使用体验？

研究问题三：用户是否理解提醒依据，是否愿意接受、纠正和持续使用这种桌宠交互？

系统识别的是可观察动作和声音。皱眉不等于痛苦，叹气不等于沮丧，出现手机不等于娱乐；低头也可能是在读书。论文应报告这些边界，不将系统描述为心理诊断工具，也不凭短期试用声称提高学习成绩。

## 二 应用场景与功能范围

### 2.1 典型使用流程

用户启动桌宠 → 输入本次学习目标和时长 → 分别选择是否开启摄像头、麦克风 → 完成简短校准 → 开始学习 → 系统按线索适时反馈 → 用户选择继续、休息或纠正 → 查看本次学习摘要。

首次使用提供摄像头取景引导，让画面覆盖脸部、上半身和可能拿手机的区域。笔记本摄像头看不到的桌面和手机，系统无法可靠检测；测试前必须确认视野。多人、严重遮挡、光线过暗或设备不可用时进入“状态未知”，保留计时和手动互动。

### 2.2 功能优先级

| 功能 | 第一版要求 | 优先级 |
| --- | --- | --- |
| 桌面宠物 | 透明悬浮、拖动、缩放、托盘菜单、气泡；待机、关心、提醒、鼓励等至少4种动作 | 必做 |
| 学习任务 | 任务名称、开始／暂停／结束、学习时长、休息提醒 | 必做 |
| 视觉感知 | 手机目标检测、手与手机关系、头部姿态、皱眉动作候选、无人／低质量状态 | 必做 |
| 音频感知 | 叹气声音候选；区分或抑制说话、咳嗽、音乐等常见干扰 | 必做且尽早验证 |
| 决策与反馈 | 时间窗口、证据融合、反馈优先级、冷却、静音、误判纠正 | 必做 |
| 记录与设置 | 本地会话和事件摘要、删除数据、分别关闭摄像头／麦克风 | 必做 |
| 语音与对话 | 文字转语音；按住说话、短对话、学习问题答疑 | 语音播报建议做；自由对话选做 |
| 高级表现 | 三维宠物、口型同步、多角色、账号云同步、手机端 | 后续扩展 |

这里的“必做”指完成实现、测试及结果报告，不代表所有场景均能达到预期精度。叹气若效果不足，应如实保留实验性标识并报告失败条件，不能用手动按钮代替自动识别后声称已经完成。

## 三 总体架构与技术栈

### 3.1 系统架构

输入层包含摄像头视频、麦克风音频、任务计时和用户按钮。感知层分别输出手机、手部、眉部动作、头部姿态、叹气等候选事件，并附带时间戳、模型分数与数据质量。决策层对齐近期事件，结合任务状态、个人基线和提醒历史决定是否反馈。表现层切换桌宠动作、显示气泡或播放语音。存储层只记录必要摘要。

处理路径为：采集 → 质量检查 → 独立感知 → 事件时间窗口 → 决策与冷却 → 桌宠反馈 → 用户纠正与本地记录。音频播放期间应抑制自触发，设备断开应能恢复或降级。

### 3.2 推荐技术栈

| 模块 | 推荐技术 | 用途与选型理由 |
| --- | --- | --- |
| 开发语言 | Python 3.11作为候选起点，按依赖实测锁定版本 | 统一界面、模型推理与实验脚本，减少语言切换 |
| 桌面界面 | PySide6／Qt Widgets | 无边框透明窗口、动画绘制、气泡、菜单、设置和托盘 [1] |
| 宠物素材 | 透明 PNG 序列帧或 GIF，Qt 定时器／QMovie | 先实现二维角色；动作统一尺寸、锚点和透明边缘 |
| 视频采集 | OpenCV | 取摄像头帧、缩放、裁剪、预览和调试 |
| 脸部与手部 | MediaPipe Tasks Face Landmarker、Hand Landmarker | 获取脸部关键点、表情形变系数和手部关键点 [2][3] |
| 手机检测 | Ultralytics YOLO11n 预训练检测模型 | 用已有手机类别建立基线，再决定是否微调；也可实测比较其他小模型 [4][5] |
| 叹气检测 | sounddevice + MediaPipe Audio Classifier + YAMNet | 本地采音与声音事件分类；YAMNet 类别表包含 Sigh [6][7] |
| 规则与存储 | Python 状态机、NumPy、SQLite、JSON配置 | 融合、冷却、会话、事件摘要和用户偏好 |
| 语音输出 | PySide6 QTextToSpeech 或预录提示音 | 调用可用的系统语音，先检查目标电脑的中文语音引擎 [8] |
| 实验与交付 | scikit-learn、Matplotlib、Git、PyInstaller | 评估指标、绘图、版本管理和 Windows 打包 |

推荐采用 Python 单应用结构，无须第一版同时搭建网站、服务器和数据库服务。界面运行在主线程，采集与推理放在后台工作线程；若实测存在阻塞，再拆为独立推理进程。通过有界队列传递数据，视频优先处理新帧，避免排队越积越多。

首轮性能参数可从640×480采集、视觉推理5—10次／秒、宠物动画12—24帧／秒开始。手机、脸部和手部可以采用不同推理频率。以上均为调试起点，需在自己的电脑上测量，不能引用模型在其他设备上的速度当作系统性能。

PyTorch 通常随 YOLO 开发环境使用；ONNX Runtime 仅在优化和导出确有需要时引入。先锁定一组经过验证的依赖及模型文件，再开展功能开发。Ultralytics 官方提供 AGPL-3.0 与企业许可选项，课题选型需记录具体代码、权重及素材许可，公开发布前按实际用途核对 [9]。

## 四 手机相关行为与皱眉动作识别

### 4.1 手机使用相关线索

第一步，用 YOLO 检测画面中的手机，获得目标框与模型分数。COCO 类别中有 cell phone，但模型只回答“哪里像手机”，不会直接给出“正在玩手机” [4][5]。

第二步，用手部关键点估计手与手机框的接近关系，并通过连续帧检查稳定性。手机摆在桌面、短暂拿起手机、拿笔及拿计算器，应作为重要反例。手与手机接近属于候选证据，仍不能保证已经拿住或操作手机。

第三步，结合相对个人正视基线的头部朝向变化、持续时间及任务状态，输出“疑似持续使用手机”。头部姿态可以由脸部关键点与姿态估计方法获得，但低头只是辅助证据，不能替代精确视线估计。

建议初始规则：在最近10秒窗口内，手机与手部关系持续满足至少7秒，且有相应头部姿态证据，才产生提醒候选。短暂漏检允许小范围容错；脸部或手部长期不可见时降低可靠性或弃判。具体分数阈值与时长只能用开发集调整，测试前冻结。

反馈示例：“要继续刚才的学习任务吗？”提供“继续学习”“我在查资料”“稍后提醒”。用户确认在查资料后，暂停本类提醒一段时间。系统不读取手机屏幕内容，不将手机相关时间直接计为分心时间。

### 4.2 皱眉动作候选

MediaPipe Face Landmarker 提供脸部关键点和表情形变系数，可用于观察眉部动作 [2]。可从 browDownLeft、browDownRight 等系数和眉眼几何变化建立规则；这些系数是模型输出，不是“难过概率”。

首次校准可安排20—30秒自然表情、正视和正常低头样本，以中位数及波动范围建立个人基线。开发时可另采示范皱眉用于阈值调试；自然表情校准不等于训练出了情绪分类器。

对信号平滑后，要求相对基线变化维持约2—3秒，再输出皱眉候选。设置不同的进入和退出阈值，减少动作边界抖动。侧脸、反光眼镜、脸部太小等情况下标记低质量；眯眼、思考和阅读小字应列入反例。

皱眉单独出现时以轻微关心动作为主，避免马上播报。若用户愿意回应，再询问“这道题有点卡住了吗？”并提供“没事”“想休息”“需要帮助”。

## 五 叹气声音检测与语音交互

### 5.1 叹气检测路线

叹气需要麦克风。应将任务定义为“声音事件检测”，而非把所有音频先转成文字。语音识别主要识别说话内容，语音活动检测主要区分语音与非语音，两者都不能直接替代叹气检测。

先用 YAMNet 预训练模型做基线。官方类别表包含 Sigh、Breathing、Cough、Throat clearing、Speech、Music 等，可用于候选检测和干扰分析；存在类别不保证在笔记本麦克风上足够准确 [6][7]。

建议采集16 kHz单声道音频，并按所用模型接口要求组织输入；使用短时环形缓存和约1—2秒分析窗口，逐步更新结果。目标叹气分数应结合环境噪声、常见混淆类别及连续窗口判断，而非检测到一次高分就打断用户。模型分数需校准，不能直接解释为真实发生概率。

第2周即进行声音可行性试验：收集少量自有叹气、呼吸、咳嗽、吹气、说话、键盘声和背景音乐片段，检查混淆情况。能量门限可用于过滤明显静音，但不能仅用语音活动检测筛掉非语音，否则可能漏掉叹气。

### 5.2 效果不足时的改进

先检查麦克风距离、采样格式、背景噪声和分段方式。若仍不满足要求，再尝试“冻结预训练音频特征提取器 + 小分类器”，与直接使用预训练分数比较；可用逻辑回归或支持向量机建立轻量基线，避免一开始从零训练大型音频网络。

数据需覆盖普通呼吸、清嗓、风噪、椅子声及电脑外放声音。采集与测试应跨人、跨会话。小规模表演性叹气只能证明受控条件下的可行性，不能代表自然学习场景的泛化效果。

### 5.3 语音交互范围

第一版使用气泡和少量预设中文语音即可，例如“已经认真学了一会儿，要休息一下吗？”播放期间以及短暂尾音期暂停或屏蔽音频事件触发，防止系统听到自己的声音；恢复后清除过期候选。

按住说话的语音指令和自由对话属于后续能力。若添加，可评估 faster-whisper 做语音转写 [10]，再做意图识别。大语言模型只接收必要的结构化事件和用户输入，用于润色短句或答疑；触发时机、冷却和权限仍由规则模块控制。核心闭环不依赖云端模型。

## 六 多模态融合与陪伴策略

### 6.1 事件融合与时间对齐

“摄像头识别一个动作，随后播放一句话”体现了感知与反馈，但若要突出多模态研究价值，需要展示声音、视觉和任务上下文怎样共同改变决策。例如同一段时间内的皱眉与叹气，比一次孤立的眉部动作更值得发起一次可拒绝的关心；是否更合适必须通过实验验证。

所有感知模块共享同一单调时间基准，事件记录起止时间、来源、分数、质量和过期时间。融合只组合时间接近且质量有效的事件，不能把几分钟前的皱眉与刚刚的叹气拼成一次证据。低质量或缺失是“未知”，不是“正常”。

### 6.2 初始决策规则

| 证据与上下文 | 建议反馈 | 触发约束 |
| --- | --- | --- |
| 仅手机出现，或仅低头 | 暂不主动提醒 | 缺少手部关系或持续时间证据 |
| 手机与手部关系持续存在，并有头部姿态辅助 | 温和提示返回任务 | 学习中；近期没有“查资料”豁免 |
| 仅短暂皱眉，或单次弱叹气候选 | 记录或轻微动作反馈 | 不直接判断情绪，不频繁播报 |
| 皱眉与叹气事件在约5秒内共同出现 | 询问是否休息或需要帮助 | 两路质量有效；满足各自阈值 |
| 连续学习达到用户设定时长 | 提供休息建议 | 定时提醒与传感器提醒合并 |
| 设备不可用、无人或多人导致归属不明 | 保留计时，暂停相关推断 | 清空过期证据并显示状态 |

这些规则是待验证的产品假设。无需强求所有功能都同时使用音视频：手机相关行为主要由视觉支持，声音的作用主要体现在关心反馈。不能把“视觉单独做不了的音频任务”混入比较后据此声称融合优于视觉。

### 6.3 防止提醒变成打扰

任务状态、感知状态和反馈状态分开维护：任务可处于待机、学习、休息；感知事件可并行存在；反馈只允许一个最高优先级动作执行，并有独立冷却计时器。

建议初始全局主动提醒间隔不少于90秒，同类提醒间隔约3分钟。用户主动点击可即时回应。多条提醒重叠时合并，用户选择“稍后”或“没事”后延后同类反馈。提醒优先级可按用户请求、休息到点、关心候选、手机候选设置，再通过试用调整。

提供“刚才识别错了”、摄像头与麦克风开关、静音、暂停陪伴等直接入口。用户纠正先用于本次会话的抑制和偏好调整；未经验证，不在后台自动重训模型。

### 6.4 一次完整交互示例

用户开始25分钟阅读任务；第8分钟出现持续眉部动作，随后出现高质量叹气候选。系统检查时间接近、仍在学习且不处于冷却期，桌宠切换关心动作，显示“辛苦啦，要休息一下，还是继续？”用户选择“继续”，桌宠恢复待机并进入冷却。若用户选择“识别错了”，记录纠正并降低本次会话的打扰频率。

## 七 数据采集与实验设计

### 7.1 先建立可复现的小型测试集

建议开发采集阶段邀请8—12名知情同意的成年人，每人至少2次独立会话，每次约10—15分钟，分散到不同光照和背景声音条件。场景包含正常阅读、看键盘、拿笔、手机放桌面、拿手机查资料、持续手机操作、皱眉、叹气，以及相应反例。该规模适合原型验证，不足以支持广泛人群结论。

分别标注可观察事实：手机是否可见、是否持握／操作、眉部动作起止、叹气起止。手机用途和是否希望收到关心应由任务记录与用户确认获取，不能只靠视频猜测。对皱眉或叹气标签抽取部分样本由第二位标注者复核，报告一致性和分歧处理方式。

先按参与者划分开发集、验证集、测试集，例如约60%／20%／20%，人数较少时采用按人交叉验证并保留最终测试会话。禁止随机拆相邻帧或重叠音频片段后分到不同集合。个人校准仅使用该用户单独的短校准段，不能查看正式测试标签；论文需分别说明是否使用个人校准。

### 7.2 分层评估与初始目标

以下数值是立项阶段的验收目标，不是已有实验结果。开发结束后报告全部实测值及未达标原因，并按不同光照、噪声、是否戴眼镜等条件分组查看错误。

| 层次 | 指标及计算口径 | 建议目标 |
| --- | --- | --- |
| 感知事件 | 按类别报告 Precision、Recall、F1及样本数；不能只报总体准确率 | 手机相关行为、皱眉候选F1争取≥0.80；叹气F1争取≥0.70 |
| 提醒策略 | 无需提醒时仍触发的主动提醒次数／有效学习小时；辅以用户接受和纠正比例 | 误提醒争取≤2次／小时；同时报告漏提醒 |
| 系统延迟 | 时间条件已经满足到气泡出现的P50／P95；与规则等待时间分开 | P95争取≤2秒，注明测试设备与负载 |
| 稳定性 | 连续运行、设备拔插、无网络、恢复感知和退出释放 | 连续运行60分钟无崩溃，队列和内存不持续增长 |
| 使用体验 | 提醒有用、打扰、陪伴感、可控性等1—5分问卷与访谈 | 有用性均值争取≥3.5，打扰均值争取≤2.5；报告分布 |

对连续事件合并重复预测，按预先冻结的规则一对一匹配真值。叹气可采用起点容差约1秒，皱眉和手机相关行为可采用事件时间交并比≥0.5；同时报告漏检与重复触发。窗口长度、匹配容差和指标实现必须在查看最终测试结果前确定。

### 7.3 对照与消融实验

实验一验证感知质量：手机检测单独使用，对比加入手部关系、头部姿态及时间窗口；皱眉固定阈值对比个人校准；叹气比较预训练基线与必要时的小分类器。每次只改变待研究因素，保持数据划分和其他参数一致。

实验二验证关心策略：在相同的候选关心事件上，比较视觉单独触发、音频单独触发、音视频联合触发。再比较有无持续时间和冷却机制。单独报告各策略可覆盖的事件、提醒准确性与遗漏，避免联合规则仅靠少提醒来获得表面优势。

实验三进行体验试用：建议12—20名成年人分别体验“定时提醒桌宠”和“多模态桌宠”，每个条件约20—25分钟，使用难度相近但不重复的学习材料，平衡体验顺序。尽可能与开发采集参与者分开；若重合，应明确披露。所有条件使用相同形象和基础反馈，减少外观差异干扰。

试用后收集提醒是否合时宜、有用、打扰、信任及可控性，并访谈误判经历。小样本优先报告配对差异、分布和不确定性；自然发生的叹气可能很少，受控识别试验与自然体验结果要分开。对学习任务完成量只能作探索性观察。

## 八 开发进度与阶段验收

### 8.1 十二周计划

| 周次 | 工作重点 | 可检查的阶段产物 |
| --- | --- | --- |
| 第1周 | 补齐Python／Qt基础，确定范围与界面草图，验证依赖 | 最简单桌宠窗口、摄像头预览、麦克风采集分别可运行 |
| 第2周 | 打通感知基线，优先验证叹气与手机视野 | 各类原始输出与错误样例；决定声音改进路线 |
| 第3周 | 完成透明桌宠、气泡、拖动、托盘和学习计时 | 手动注入事件可触发动画和提醒；注入仅用于调试 |
| 第4周 | 手机、手部关系、头部姿态及连续时间判定 | 正反例测试视频和第一版手机相关行为报告 |
| 第5周 | 皱眉候选、个人基线、视觉质量判断 | 校准流程、动作曲线及误判清单 |
| 第6周 | 音频流水线、叹气校准、回声抑制；必要时轻量分类 | 叹气独立测试及混淆分析 |
| 第7周 | 统一事件时间戳、融合规则、状态、冷却、反馈入口 | 真实感知到桌宠动作的完整闭环 |
| 第8周 | 本地记录、设置、异常处理与首次打包 | 可安装原型；冻结主要功能及实验方案 |
| 第9周 | 完成独立数据标注、阈值冻结与正式评测 | 感知、时序规则、融合策略的实验结果 |
| 第10周 | 体验试用、访谈和配对分析 | 问卷数据、打扰与误判总结、改进建议 |
| 第11周 | 修复问题、整理图表，撰写论文主体 | 可复现实验、论文初稿、系统结构图 |
| 第12周 | 全流程回归、演示视频、文档和答辩准备 | 最终软件、论文、操作说明和答辩材料 |

第2周是可行性检查点，第7周是闭环检查点，第8周以后避免加入大型新模块。若周期只有8周，应压缩自由对话、语音输入、复杂角色和深度训练，保留三类感知、融合、误判反馈和必要实验；效果不足的功能如实报告。

### 8.2 第一周可以直接开始的事情

第1—2天：确定电脑配置、可投入时长和最终要求；创建代码仓库与隔离环境；分别运行透明窗口、摄像头、麦克风三个最小示例，记录依赖版本。

第3—4天：用临时透明角色做出拖动、右键菜单、文字气泡和25分钟学习计时；通过手动事件模拟“手机候选”“皱眉候选”“叹气候选”，先验证反馈流程。

第5—7天：接入脸部和手机预训练模型，确认真实机位下能看到什么；保存经同意的少量开发样本，准备第2周的叹气测试。第一周的完成标准是“输入能采到、角色能显示、事件能推动交互”，不追求完整情绪识别。

## 九 资源投入与风险控制

### 9.1 硬件与工作量

优先使用现有 Windows 电脑、摄像头和麦克风。建议16 GB内存作为开发起点，CPU先跑小模型并测量；独立显卡属于优化资源，不应成为第一版必须购买的条件。若打算训练或微调，先验证数据价值，再使用已有实验室或短时计算资源。

硬件新增需求由第2周的真实采集和性能测试决定。核心离线方案不需要持续购买大模型API。预算应分为采集设备、角色与音频素材、实验参与补偿、可选计算资源四项，依据实际报价和学校要求填写，不预设必须购买的服务。

### 9.2 主要风险与应对

| 风险 | 具体应对 |
| --- | --- |
| 叹气弱、少且易混淆 | 尽早做可行性试验；采集强反例；校准阈值；必要时训练小分类器；报告未知和失败条件 |
| 摄像头看不到手机或手 | 提供机位预览；限定可见区域；低质量弃判；不把“没看见”视为“没使用” |
| 皱眉被误解释为负面情绪 | 只输出动作候选；联合上下文；用可拒绝的询问确认 |
| 模型同时运行导致卡顿 | 后台推理、降低采样、有界队列、按需启用手部检测、必要时模型导出优化 |
| 提醒频繁或用语生硬 | 冷却、优先级、延后提醒、可选语音及用户纠正；在用户试用中专门评价打扰 |
| 依赖兼容或打包失败 | 第1周锁定可运行环境；第8周前完成首次打包；在另一台目标Windows电脑测试 |
| 数据过少导致结果虚高 | 按人／会话划分；独立测试；报告数量和失败样例，不把受控表演当作自然场景 |

### 9.3 数据与用户控制

默认在本地内存中处理音视频，仅保存会话时间、候选事件、触发依据和用户选择等摘要。事件摘要也可能包含个人行为信息，应支持查看、导出和删除，设置明确的保留期限，不在普通日志中写入原始媒体。

科研采集采用单独开关、单独说明和知情同意；原始音视频与日常运行日志分开保存，使用参与者编号并限制访问，按约定时间删除。若学校要求伦理审查，应在招募和采集前完成。日常模式不做人脸身份识别，默认不上传画面和原始音频；未来接入云端服务时另外说明实际发送的数据。

## 十 预期成果与论文组织

### 10.1 最终交付物

软件成果：Windows 可运行程序及完整源码，具备二维桌宠、任务计时、手机相关视觉线索、皱眉候选、叹气候选、融合决策、用户纠正和本地记录功能；附带模型清单、依赖锁定文件和运行说明。

研究成果：数据采集与标注规范、匿名化结果、按参与者划分的实验清单、评估脚本、单模块与融合对照、误判分析和用户试用结果。公开材料不包含未获许可的参与者原始音视频。

展示成果：系统架构图、交互流程图、实验图表、约3—5分钟演示视频、论文和答辩材料。演示应同时展示成功识别、用户纠正、低质量弃判、设备关闭及冷却机制，体现系统边界。

### 10.2 可主张的课题贡献

可将贡献定位为：面向学习场景的多模态事件组织方法；结合个人基线、时序窗口和质量判断的反馈策略；支持用户纠正且控制打扰的桌宠交互；以及覆盖识别和体验的原型实证评估。

贡献应由实验支撑。调用现成模型本身不是新算法，也不应把“用了摄像头、麦克风和大模型”直接当作创新结论。若学院要求算法创新，可在基线完成后选定一个问题深入，例如以验证集比较“简单规则”和“轻量学习式融合”，不同时展开多个大型模型训练方向。

### 10.3 建议论文结构

第一章介绍问题、目标和边界；第二章整理多模态交互、桌面陪伴和事件识别相关工作；第三章描述需求、交互与总体架构；第四章给出感知、校准、融合与提醒策略；第五章说明实现和运行机制；第六章报告数据、实验、用户试用与局限；第七章总结与展望。

下一步最有价值的产物是一个“透明宠物 + 计时 + 气泡 + 三个手动测试事件”的小原型，并在同一周分别验证摄像头和麦克风。这样既能尽早看到成品形态，也能在投入大量开发前发现视野、声音质量和依赖问题。
